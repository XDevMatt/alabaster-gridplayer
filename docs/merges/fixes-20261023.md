# Fixes after the upstream merge, 2026-10-23

These fixes are on branch `fixes-20261023`. It starts from
`merge-upstream-20261023` at `1425435`, which is `xdev/master`. Nothing has
been pushed.

## 1. SubtitleCat broke every request after it read browser cookies

`gridplayer/plugins/subtitlecat/session.py` (`_ytdlp_reader`) imported
`yt_dlp.cookies` but never called `untangle_percent_re()`. Every other yt-dlp
import in the app calls it (see `gridplayer/utils/percent_re.py`).

When streamlink had been imported first, yt-dlp's wrapper and streamlink's
wrapper broke urllib3's percent regex. After that, every request failed on
its host name, not only the SubtitleCat ones.

The fix calls the repair right after the import.

- New test: `tests/test_percent_re.py::test_reading_subtitlecat_cookies_leaves_requests_working`.
  In a fresh interpreter it imports streamlink, then runs the plugin's cookie
  reader, then checks that requests still keeps a URL's `%2f`. It fails
  without the fix.
- The existing test `test_every_import_of_yt_dlp_is_followed_by_the_repair`
  now passes.

## 2. HLS links did not play

Two faults stacked on top of each other. Only the first one is the reason
plain HLS links failed. The second one broke every link that really needs
the callbacks.

### Root cause: yt-dlp's default headers sent every link to the callbacks

The fork replaced upstream's loopback stream proxy (`hls_proxy` and
`dash_proxy`) with two routes:

- HLS and DASH manifests go to VLC as URLs.
- Streams that VLC cannot fetch go through libVLC media callbacks fed by
  yt-dlp.

`_get_stream_protocol` chooses the route. It sent a stream to the callbacks
whenever `_headers_need_callback` found a header other than User-Agent or
Referer.

yt-dlp puts its own `std_headers` (Accept, Accept-Language, Sec-Fetch-Mode)
on every format it returns, whether the site asked for them or not. So every
format yt-dlp read went to the callbacks, plain HLS included. Upstream has no
such check: it gives HLS to its proxy, or to VLC.

The fix, in `gridplayer/utils/url_resolve/resolver_yt_dlp.py`
(`_headers_need_callback` and `_is_ytdlp_default_header`): a header counts
only when its name and value are not yt-dlp's own default. An Origin, Cookie
or Authorization header still sends the stream to the callbacks, and so does
an Accept-Language the site changed.

Tests in `tests/test_resolver_yt_dlp_streams.py`:

- Live and VOD HLS that carries only `std_headers` is `hls`, with the variant
  URL. This test fails without the fix.
- Each of the four real headers above still gives `callback`.

### Second fault: the callback source never delivered a byte

`gridplayer/utils/ytdlp_byte_source.py` set up its stand-in stdout for
yt-dlp by assigning `self.encoding` on an `io.TextIOBase`. That attribute is
read-only, so the download thread died before yt-dlp started.

The failure happened outside the `try`, so no error was recorded. `read()`
then saw a finished thread and returned an empty stream, and VLC reported
"Player error" at once.

The stand-in also swapped `sys.stdout` for the whole process on each
download. Two cells using the callbacks at the same time would take each
other's bytes, and the first one to finish would put the real stdout back
while the other was still downloading.

The fix:

- One process-wide `_ThreadStdout` gives a byte source's own thread its
  queue. Every other thread still writes where it did before.
- Everything before the download is now inside the `try`.

Tests in `tests/test_ytdlp_byte_source.py`:

- A real yt-dlp download from a local server arrives byte for byte.
- Two downloads at once each get their own bytes, while the app's own
  `print` still works.
- A failure before the download starts is reported as an error, not as an
  empty stream.

All three fail without the fix.

### Security choices kept

- **No listener:** nothing new listens on a socket.
- **URL scheme allowlist:** unchanged. VLC gets the HLS variant URL that
  yt-dlp resolved from the URL the user opened, as the fork's routing already
  did for live HLS.
- **yt-dlp and Deno:** the pinned yt-dlp, the vendored Deno and the opt-in
  for runtimes on PATH are untouched.

## 2a. Video with separate audio (the `dubs` scenario): options A and B, C later

### Why the old route could not work

When a stream's audio came separately, the fork asked yt-dlp to merge the
two through the callbacks, with format `video+audio` and output to `-`. That
cannot work as built:

1. **The wrong output format.** yt-dlp refuses `merge_output_format:
   "mpegts"`: "The extracted extension ('mpegts') is unusual and will be
   skipped for safety reasons". This is what `dubs` hit.
2. **ffmpeg writes to the process's stdout.** yt-dlp merges to `-` with
   `FFmpegFD`, which writes to `pipe:1`: the process's real file
   descriptor 1, not the callback queue.
3. **There is no ffmpeg on Windows.** The Windows build ships VLC but no
   ffmpeg executable.

The owner chose: A now, then B where it measures well, C (ffmpeg) only for
what B cannot do. No relay: Alabaster starts no local listener.

### A. The manifest, whole (done, `c19c77a`)

When the silent video and every audio track come from one manifest (an HLS
master playlist or a DASH MPD, yt-dlp's `manifest_url`), the URL is http(s),
and nothing needs the callbacks, VLC gets the manifest itself:

- HLS as `hls`, DASH as `direct`; VLC's adaptive demuxer pairs video and
  audio. No listener, no ffmpeg, no merge.
- **Quality:** the rung picked in the menu goes to VLC as
  `:adaptive-maxheight=N`. VLC keeps its own adaptive logic under that cap,
  so it can still step down on a slow network. Rungs of one MPD are no
  longer collapsed into "Adaptive".
- **Language:** the audio tracks are VLC's own. Picking a language in the
  existing audio track menu selects VLC's track, with no reload
  (`apply_wanted_track`), and the language shown is the one VLC is playing.
- The scheme allowlist, pinned yt-dlp, vendored Deno and the PATH opt-in are
  unchanged.

Measured with VLC 3.0.24: an HLS master and an ffmpeg-made MPD (one audio
adaptation set per language) both play, list both languages, honour
`adaptive-maxheight`, and seek.

Tests: `tests/test_whole_manifest.py` (20; 12 fail without the change), the
real-app scenarios `dubs` (HLS master) and the new `dubs_dash` (MPD), both
passing, and `TestOptionA` in `tests/real_app/test_separate_media_vlc.py`.
A covers the dubs scenario completely.

### B. A plain video file with its sound as an input slave (done for whole MP4, `4dbae16`)

Tried on local test media served over plain http by a test-only server
(the app has none): a video that flashes white every second and audio that
beeps every second. libvlc's video and audio callbacks give when VLC shows
each flash and schedules each beep, on one clock, so the offset between
them is measured directly. These are VLC's scheduled times, not the sound
card's.

| Pair (video + audio slave) | Plays | A/V offset | Drift | Seeks back and forth |
|---|---|---|---|---|
| muxed faststart MP4 (reference) | yes | about 0 ms | none | all |
| faststart `video.mp4` + `audio.m4a` | yes | about -0.1 ms | none over 65 s | 24/24 (3 runs of 8); see below |
| fragmented MP4 (empty_moov, `+dash+global_sidx`, ffmpeg DASH single file) | yes | constant | none | **no**: `is_seekable` is 0 and seeks are ignored, muxed or not, local or http; as master or slave the slave seeks and the video doesn't, so they desync |
| WebM VP9 + Opus | yes | constant -7.6 ms | none | **no**: 0/8 (ffmpeg default) or 3/8 (cues up front) per run; sound lost or playback frozen at the target. A muxed WebM seeks 8/8 |

Constant offsets (Opus -7.6 ms, AAC in fragmented MP4 about 21 to 39 ms)
are encoder delay, not drift.

Since then, for the whole MP4 + M4A pair: 36 more runs of 4 to 7 seeks each
(including 5 with every core busy), every seek landed with picture and
sound, offset unchanged. Before those, in 4 of 10 runs, sound stopped for
good after the first seek backwards (to 5 s, after 25 s): no beep
afterwards, picture fine. That was not reproduced in the 36 runs since, and
its cause was not found. It is worth watching for in use;
`TestOptionB` in `tests/real_app/test_separate_media_vlc.py` checks it on
every real-app run.

The slave was fetched with the media's `:http-user-agent` and
`:http-referrer` (checked on the server). It is not fetched with other
headers or cookies.

So B is implemented narrowly, behind the same routing:

- Only when yt-dlp returns a silent video and separate audio that are both
  plain `http` formats VLC opens itself (no callback route), not a `_dash`
  container, with extension mp4/m4a/m4v/mov, and the site's files were
  probed and found not fragmented. A failed probe leaves the stream alone.
- VLC gets the video, with the best audio file in the chosen language as an
  input slave. The stream is seekable (not marked adaptive), and it is not
  merged through the callbacks. Choosing another language picks another
  file.
- Tests: `tests/test_audio_slave.py` (17; 15 fail without the change) and
  `TestOptionB` (real VLC): plays, stays in sync, survives 5 seeks back and
  forth, headers reach the slave, and a fragmented MP4 does not seek (if
  VLC learns to, that test fails, and B can take more on).

**YouTube is not covered by B.** Its separate formats are DASH files
(`mp4_dash`, fragmented with a sidx; or WebM), which VLC 3.0.24 cannot seek
in or loses sound on. Those stay on the routes they had before B (A where they
share a manifest, the fork's own HLS playlist of a file's fragments where
that applies), and otherwise wait for C.

### What is still missing: C, ffmpeg (not built)

Callback streams (impersonation, or headers VLC can't send) with separate
audio, and YouTube-style DASH files, still have no working merge. C is the
fallback for those only: ffmpeg merges the two into the callback queue. A
callback stream has no known length and cannot seek, so C is worse than A
and B wherever they apply.

The owner has decided Alabaster will bundle ffmpeg and ffprobe ("size
doesn't matter, reliability does"). The Windows build does not ship them
yet. What bundling takes:

- **Which build.** BtbN/FFmpeg-Builds publishes static win64 and linux64
  builds of master and of release branches (`n8.1`, `n9.0`). Pin a release
  branch from a monthly build (kept two years; the floating "latest" builds
  change daily) and its SHA-256, like the vendored Deno. There are no win32
  auto-builds; the 32-bit Windows build would need one made with BtbN's
  scripts (`./build.sh win32 lgpl`), or would go without C. gyan.dev's
  Windows builds are GPL only.
- **License.** Alabaster is GPL-3.0, so both variants are allowed. The
  `lgpl` variant leaves out GPL-only libraries (libx264, libx265), which a
  remux (`-c copy`) does not need. Either way, distributing the binary means
  offering its corresponding source (the release tag plus the build
  scripts) and its license text next to NOTICE; the `gpl` variant adds the
  GPL-only libraries' sources to that offer. Recommended: `lgpl`, static,
  release branch. Sizes in the current release: win64 lgpl about 162 MB zip
  (ffmpeg, ffprobe and ffplay; ship the first two), win64 lgpl-shared about
  77 MB, linux64 lgpl about 130 MB.
- **PyInstaller (Windows).** A `scripts/fetch_ffmpeg_windows.ps1` like
  `fetch_deno_windows.ps1` (download, check the hash, unpack to
  `vendor/ffmpeg/`), then in `pyinstaller_win.spec` add
  `vendor/ffmpeg/ffmpeg.exe` and `ffprobe.exe` to `binaries` (they are
  executables with no Python imports, so `binaries`, not `datas`; the spec
  already has `upx=False`), with the same "MISSING" print as Deno. The app then
  hands yt-dlp `ffmpeg_location` pointing at the bundled folder, and only
  that one, as with Deno and the PATH opt-in.
- **Linux AppImage.** `scripts/appimage/build_docker.sh` runs on
  manylinux_2_28 (glibc 2.28), which BtbN's linux64 builds target. Copy the
  static `ffmpeg` and `ffprobe` into the AppDir's `usr/bin`; no libraries
  needed. The AppImage's VLC comes from the distro (`yum install vlc`), so
  its version is not pinned at 3.0.24 the way the Windows build's is; the
  limits above should be rechecked against it.
- **Snap.** `core22`; either `stage-packages: [ffmpeg]` (Ubuntu 22.04's
  ffmpeg 4.4, with its shared libraries, which VLC's `vlc-plugin-base`
  partly pulls in already) or a `dump` part with BtbN's static binaries for
  the same version as the other builds. The second keeps every platform on
  one ffmpeg. Strict confinement is fine: ffmpeg is called inside the snap.

### The relay and Streamlink: opt-in only

Rule: the stream relay (upstream's local listener) or a Streamlink route
that needs it may come back only as an opt-in plugin, off by default, with
a warning when it is turned on that it starts a local listener. It is never
the default, and no update or migration turns it on. See
`docs/roadmap.md`.

### Still true

- **Callback streams have no length or seeking.** A stream fed through the
  callbacks has no known length and cannot be sought, so the app treats it
  as live and its time stays at 0.

## 3. Volume: 3% steps, and mute is 0% (owner's decisions)

Before, "Audio Volume - Decrease" on a new (muted) cell showed "0%" and
changed nothing, so the `playback` scenario's "quieter" check failed. The
owner decided in two rounds. The first made the step 3% and had down on a
muted cell lower a level kept behind the mute ("Muted, 97%"); the second
replaced that with his rule, in his words: "mute isnt a hand held over the
speaker... its an instant teleport of the volume wheel to zero land. make
that universal."

**The rule: mute is volume 0%, and 0% is mute.** No level is kept behind
the mute, shown or hidden.

- **One setter.** A cell's volume and mute only change together, through
  `AudioControl._set_level` (`gridplayer/widgets/video_block_audio.py`),
  as the pair `mute_as_zero` gives (`gridplayer/utils/volume.py`): muted or
  0% is `(muted, 0.0)`, anything else is `(unmuted, volume)`. Both are sent
  to VLC each time.
- **Speaker button, M (all cells), Mute / Unmute [ALL].** Mute takes a cell
  to 0%. Unmute brings it in one step up from 0 (3% by default), not back
  to the level it had: the owner answered that unmuting does not restore.
  A cell that is already heard keeps its volume when told to unmute, so M
  on a mix of cells only changes the muted ones.
- **Volume keys and the mouse wheel.** Down at 0% stays at 0% and muted; up
  goes 0 -> 3% -> 6%. Down to 0% mutes the cell. The overlay says
  "Volume 0%"; "Muted, 97%" and its string are gone.
- **The overlay's slider.** Dragged to 0 it mutes the cell; dragged up on a
  muted cell it unmutes at that level. It always shows the cell's volume:
  hidden while the cell is muted, as before, and back at 3% on unmute.
- **New cells** start muted (`video_defaults/muted`, on), so at 0%.
  `video_defaults/volume` (100%) is what a cell gets only when new cells
  are set to start with sound.
- **Saved playlists and sessions.** `Video` pairs the two as it is read
  (`Video._mute_is_zero`, `gridplayer/models/video.py`), so:
  - a cell saved muted opens muted at 0%, and is written back as
    `is_muted: true, volume: 0.0`;
  - an old file saved muted with its volume at 100% (or any level) behind
    the mute opens muted at 0%: the level it kept is dropped, since nothing
    may be kept behind the mute;
  - a cell saved unmuted at 0% opens muted.
  The file format is unchanged; only the values a muted cell is saved with.
- **The Playlist window's video defaults** given to the cells already open
  are paired against each cell's own mute and volume as it adopts them
  (`VideoBlock.adopt_defaults`), not against a new video's: changing the
  default volume does not unmute a muted cell, and muting by default takes
  cells to 0%.
- **Step size 3%.** `player/volume_step` defaults to 3 (was 5), for the keys
  and the wheel alike, which both go through `AudioControl._step_volume`.
  Reason: he scrolls quickly, and at 5% one step was too quiet and the next
  too loud. Steps are whole percents, clamped to 0..100% and rounded to 2
  decimals, so they do not drift; 33 steps down from 100% land exactly on
  1%, then 0%.
- **Existing users' step.** The settings dialog saves every field when it
  is closed with OK, so a stored step of 5 is almost always the old default
  saved along with the rest, not a choice. On first start it is forgotten
  once, so the new default applies, and the marker
  `migrations/volume_step_3` is set; a 5 picked afterwards is kept, and any
  other stored step is never touched (`_Settings._migrate_volume_step_default`
  in `gridplayer/settings.py`).

Tests: `tests/test_wheel_volume.py` (3% by default for keys and wheel, no
drift, the old step moved once, and `TestMuteIsZero` with the muted-cell
tests: new cells at 0%, old and new saved files, speaker button to 0% and
back at one step, unmuting a heard cell, the slider, the video defaults);
21 of its tests fail without the mute change. `tests/test_playlist_window.py`
pairs the video defaults. The `playback` scenario expects a new cell muted
at 0, down to stay at 0 and muted, up to 0.03, mute to 0 and unmute to 0.03,
and M on every cell to 0.03 and then back to 0.
