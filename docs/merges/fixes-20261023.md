# Fixes after the upstream merge, 2026-10-23

These fixes are on branch `fixes-20261023`. It starts from
`merge-upstream-20261023` at `1425435`, which is `xdev/master`. Nothing has
been pushed.

## 1. SubtitleCat broke every request after it read browser cookies

`gridplayer/plugins/subtitlecat/session.py` (`_ytdlp_reader`) imported
`yt_dlp.cookies` but never called `untangle_percent_re()`. Every other yt-dlp
import in the app calls it (see `gridplayer/utils/percent_re.py`).

When streamlink had been imported first, yt-dlp's wrapper and streamlink's
wrapper broke urllib3's percent regex. After that, every request failed on
its host name, not only the SubtitleCat ones.

The fix calls the repair right after the import.

- New test: `tests/test_percent_re.py::test_reading_subtitlecat_cookies_leaves_requests_working`.
  In a fresh interpreter it imports streamlink, then runs the plugin's cookie
  reader, then checks that requests still keeps a URL's `%2f`. It fails
  without the fix.
- The existing test `test_every_import_of_yt_dlp_is_followed_by_the_repair`
  now passes.

## 2. HLS links did not play

Two faults stacked on top of each other. Only the first one is the reason
plain HLS links failed. The second one broke every link that really needs
the callbacks.

### Root cause: yt-dlp's default headers sent every link to the callbacks

The fork replaced upstream's loopback stream proxy (`hls_proxy` and
`dash_proxy`) with two routes:

- HLS and DASH manifests go to VLC as URLs.
- Streams that VLC cannot fetch go through libVLC media callbacks fed by
  yt-dlp.

`_get_stream_protocol` chooses the route. It sent a stream to the callbacks
whenever `_headers_need_callback` found a header other than User-Agent or
Referer.

yt-dlp puts its own `std_headers` (Accept, Accept-Language, Sec-Fetch-Mode)
on every format it returns, whether the site asked for them or not. So every
format yt-dlp read went to the callbacks, plain HLS included. Upstream has no
such check: it gives HLS to its proxy, or to VLC.

The fix, in `gridplayer/utils/url_resolve/resolver_yt_dlp.py`
(`_headers_need_callback` and `_is_ytdlp_default_header`): a header counts
only when its name and value are not yt-dlp's own default. An Origin, Cookie
or Authorization header still sends the stream to the callbacks, and so does
an Accept-Language the site changed.

Tests in `tests/test_resolver_yt_dlp_streams.py`:

- Live and VOD HLS that carries only `std_headers` is `hls`, with the variant
  URL. This test fails without the fix.
- Each of the four real headers above still gives `callback`.

### Second fault: the callback source never delivered a byte

`gridplayer/utils/ytdlp_byte_source.py` set up its stand-in stdout for
yt-dlp by assigning `self.encoding` on an `io.TextIOBase`. That attribute is
read-only, so the download thread died before yt-dlp started.

The failure happened outside the `try`, so no error was recorded. `read()`
then saw a finished thread and returned an empty stream, and VLC reported
"Player error" at once.

The stand-in also swapped `sys.stdout` for the whole process on each
download. Two cells using the callbacks at the same time would take each
other's bytes, and the first one to finish would put the real stdout back
while the other was still downloading.

The fix:

- One process-wide `_ThreadStdout` gives a byte source's own thread its
  queue. Every other thread still writes where it did before.
- Everything before the download is now inside the `try`.

Tests in `tests/test_ytdlp_byte_source.py`:

- A real yt-dlp download from a local server arrives byte for byte.
- Two downloads at once each get their own bytes, while the app's own
  `print` still works.
- A failure before the download starts is reported as an error, not as an
  empty stream.

All three fail without the fix.

### Security choices kept

- **No listener:** nothing new listens on a socket.
- **URL scheme allowlist:** unchanged. VLC gets the HLS variant URL that
  yt-dlp resolved from the URL the user opened, as the fork's routing already
  did for live HLS.
- **yt-dlp and Deno:** the pinned yt-dlp, the vendored Deno and the opt-in
  for runtimes on PATH are untouched.

## 2a. Decision needed: video with separate audio (the `dubs` scenario)

When a stream's audio comes separately, the fork asks yt-dlp to merge the
two through the callbacks, using format `video+audio` with output to `-`.
This cannot work as built:

1. **The wrong output format.** `merge_output_format: "mpegts"` is refused by
   yt-dlp: "The extracted extension ('mpegts') is unusual and will be skipped
   for safety reasons". This is what `dubs` hits now.
2. **ffmpeg writes to the process's stdout.** yt-dlp merges to `-` with
   `FFmpegFD`, which starts ffmpeg with `Popen(args, stdin=PIPE)` and writes
   to `pipe:1`. The output goes to the process's real file descriptor 1, not
   to the callback queue, so VLC would still get nothing.
3. **There is no ffmpeg on Windows.** The Windows build ships VLC but no
   ffmpeg executable, so yt-dlp cannot merge there at all.

These options were tried here with VLC 3.0.24 on the `dubs` test media:

- **A. Give VLC the HLS master playlist.** VLC plays it, lists both audio
  renditions by language ("audio_2 - [English]", "audio_3 - [Spanish]"), and
  switches between them while playing. There is no listener and no ffmpeg.
  - Cost: language and quality choices would map to VLC's own tracks and
    adaptive choice (for example `:adaptive-maxheight`), not to separate
    yt-dlp formats.
  - Limit: this works only where audio and video share a manifest (HLS
    master, DASH MPD). Separate plain-file audio, as on YouTube, is not
    covered.
- **B. Give VLC the video, with the audio URL as an input slave.** This
  needs no listener. The tried case was the HLS variant with the audio
  rendition as slave. It loaded but did not advance (time stayed 0), so it
  does not work for HLS. It might work for plain http files, as the fork
  already does for external audio, but that was not tried.
- **C. Ship ffmpeg, and have the byte source run the merge itself** with
  ffmpeg's stdout piped into the queue.
  - Cost: adds a binary of about 80 MB and its supply chain.
  - Limit: ffmpeg fetches the media itself, so there is no browser
    impersonation.
- **D. Bring back upstream's loopback proxy.** This reverses the fork's
  "no listener" security choice.
- **E. Play the video without its separate audio** on the callback route.
  This is a regression.

Nothing has been changed for this. Also note the following:

- **Callback streams have no length or seeking.** A stream fed through the
  callbacks has no known length and cannot be sought, so the app treats it as
  live and its time stays at 0.

## 3. The `playback` scenario's volume expectation (not changed)

**What the scenario expects** (`tests/real_app/scenarios/playback.py:30-32`):

- "Audio Volume - Decrease" on a newly opened cell makes
  `video_params.volume` lower than before.
- That is upstream's behavior. Upstream's `volume_decrease` unmutes the cell
  and takes 0.05 off the stored volume, so 1.0 becomes 0.95.

**What the fork does:**

- New cells start muted, in upstream as well:
  `gridplayer/settings.py:175`, `"video_defaults/muted": True`.
- `gridplayer/widgets/video_block_audio.py:708` `volume_decrease` calls
  `_step_volume(-1)` (line 711).
- Line 723 takes a muted cell as heard at 0 %, and the step goes down from
  there.
- Lines 727-729: when the step comes out at 0 or below, the cell stays muted.
  Its stored volume is left at 1.0, so the mute button still brings it back
  at 100 %. Only "0%" is shown.
- The step size comes from `gridplayer/utils/volume.py:51`
  (`stepped_volume`).

So the scenario's check "quieter" sees 1.0 and fails.

**Choices for the owner:**

- **Keep the fork's behavior.** "Down" on a muted cell keeps it silent and
  keeps the volume for unmuting. The scenario would then be changed to
  unmute first, or to expect the cell to stay muted at 1.0.
- **Go back to upstream's behavior.** "Down" unmutes and lowers the stored
  volume.

  than the merge (`test_percent_re` now passes), and nothing new failed.
  - The 13 failures: 12 `test_stream_proxy_*` (see below) and
    `test_network_checkup`'s "a name that does not resolve". The box's

  a known VLC bug).
  - Passed: `streams` and `callback_stream`, among the rest.
  - Failed: `dubs` (section 2a) and `playback` (section 3).

### Test PC (Windows 10, Python 3.12.10)

The run used a throwaway clone of a bundle of this branch at `12ca3fc`, with
a `uv` venv local to the repo. Temp, the uv cache and pytest's base temp
folder were all inside the clone. Nothing was installed system-wide, and the
clone was deleted afterwards.

- Full suite: **15 failed, 7164 passed, 12 skipped**, in 17 min. The old
  baseline was 145 failures in the owner's tree.
- 13 of the 15 were already in that baseline:
  - **12 `test_stream_proxy_*`:** these test upstream's loopback relay. The
    fork removed the relay, so the tests are out of date and they fail the
    same way on Linux; it is not a network problem. The owner chose to
    delete them (section 5).
  - **`test_video_errors` `test_since_the_video_began_to_open`:** Windows
    clock resolution. `time.sleep(0.01)` may not move `time.time()`.
- 2 were new compared with the baseline:
  - **`test_settings_sections` `test_headings_are_drawn_as_text_not_greyed_out`:**
    an upstream test that arrived with the merge. It fails on Windows
    offscreen with upstream's own `settings_index.py` too (tried in the
    clone), so the Alabaster heading style is not the cause. The darkest
    pixel it finds is black, not the theme's text colour. It passes on
    Linux.
  - **`test_ytdlp_byte_source` `test_two_at_once_each_get_their_own`:** a
    new test from section 2. It failed once in the full run: the second
    file's reader got an empty stream with no error, though the server
    served the file. It passed in 16 more runs on Windows, alone, with its
    file, and with the last 1,385 tests of the suite. The cause is not
    known. The likely suspect is pytest swapping `sys.stdout` between when
    the wrapper is installed and when yt-dlp reads `sys.stdout.buffer`. In
    the app nothing swaps it.
