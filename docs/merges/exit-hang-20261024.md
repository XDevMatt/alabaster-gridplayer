# Exit hang: a windowless process left after closing, 2026-10-24

Branch `exit-hang-20261024`, from `94072fb`.

## What happened

On Windows a `pythonw -m gridplayer "<video>"` was still running hours after
its window had closed. Closing hides the window first, then shuts down the
players, runs every manager's cleanup, and only then exits
(`player/managers/window_state.py`, `closeEvent`). Any wait in between that
never returned left the process running with no window.

The likeliest one was reproduced on Linux: a client that connects to the
single-instance pipe and never writes (a second start that died half way)
held the listener in a read with no timeout. Closing then sent the listener
its shutdown message, which queued up behind the silent client unread, and
waited for the listener thread for good.

## What changed

- **Instance pipe** (`utils/single_instance.py`):
  - The listener gives a client 1 s to send its message
    (`CLIENT_READ_TIMEOUT_S`), then drops it and goes on listening.
    - On Unix this is a socket timeout.
    - On Windows a synchronous `ReadFile` cannot be given one, so the read
      polls `PeekNamedPipe` and only reads what is there
      (`_read_pipe_exact`).
  - Closing waits for the listener at most 2 s, and goes on if it cannot
    reach the listener at all. The thread is a daemon.
  - A client waits at most 2 s for a busy pipe (`WaitNamedPipeW`, was
    forever) and for a Unix socket to take it.
- **Decoder process manager** (`multiprocess/process_manager.py`,
  `multiprocess/command_loop.py`, `utils/log_config.py`):
  - Its command loop is a daemon thread, joined for 2 s. The other
    command loops (players, drivers) are unchanged.
  - Reaping an exited decoder process waits 1 s.
  - Stopping the log listener waits 2 s.
- **Exit watchdog** (`utils/exit_watchdog.py`):
  - Once closing is decided (after the "save changes?" question, which
    waits on the user), a daemon thread counts 10 s.
  - If the app is still there then, it terminates every child process,
    kills the ones still alive half a second later, and ends the app with
    `os._exit(1)`. On Windows the decoder processes' job object kills them
    as well when the app goes.

## Tests

- `tests/test_exit_hang.py`: 20 on Linux, plus 2 more that run only on
  Windows (a silent client on the named pipe; a client and a busy pipe).
  - 13 of the Linux ones fail without the change.
  - The rest are a behaviour that already held (the next client is still
    heard; no countdown while the question is up) and the watchdog's own
    tests, which cannot run without its module.
  - One runs the watchdog for real in a process of its own that hangs with
    a child: the process is gone with exit code 1 and the child with it.
  - `tests/conftest.py` keeps the watchdog from ending the test run: a
    test that closes the player only records that it fired.
- `tests/real_app/test_exit.py` (real_app, Linux under xvfb) starts the app
  as a user would, `python -m gridplayer clip.mp4`, with its own data
  folder (`GP_USER_DATA_DIR`). It closes the window with `WM_DELETE_WINDOW`,
  as a window manager does, and checks that the app and every process it
  started (decoder, resource tracker) are gone within 6 s with exit code 0.
  - The variant with a silent client on the instance socket ran past 6 s
    without the change; the plain close passed either way.
  - With only the pipe fix taken out, the watchdog ended it at 10.0 s with
    exit code 1, and no child was left.

The Windows code paths (the polled pipe read, the bounded `WaitNamedPipeW`)
were not run here; the Windows-only tests above cover them on Windows.
